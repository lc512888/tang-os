1. 执行摘要 / Executive summary

Tang OS 的准确定位：将身份、不变量、人格响应策略、记忆与权限边界表达为可测试 Python 组件的 Alpha 参考实现。公开入口 Tang.process() 运行确定性的“不变量 → 人格”决策；Tang.respond() 是显式启用的 Provider 表达路径。

Accurate positioning: an alpha reference implementation expressing identity, invariants, persona response policy, memory, and permission boundaries as testable Python components. Tang.process() runs the deterministic invariant-to-persona decision path; Tang.respond() is an explicit provider expression path.

2. 当前架构 / Current architecture

关键设计 / Key design

  • 决策与表达分离：Provider 只能表达结构化决策，不应拥有或修改人格。
    Decision and expression are separate: a provider verbalizes a structured decision and must not own or mutate personality.
  • 默认离线：只有显式调用 respond() 且注入 Provider 时才可能产生网络请求。
    Offline by default: network access is possible only through explicit respond() use with an injected provider.
  • 能力与权限分离：扩展、宿主和执行器契约不自动获得操作授权。
    Capability is separate from authority: extension, host, and actuator contracts grant no automatic permission.

4. 运行数据流 / Runtime data flow

  1. 调用方创建 Tang；状态管理器启动会话。
    The caller creates Tang; the state manager starts a session.
  2. process(input) 先检查已知不变量违规，再由 PersonaRuntime 解释情绪、关系信号和响应策略。
    process(input) checks known invariant violations before persona interpretation.
  3. 返回情绪、关系、响应决策和准入结构。
    It returns emotional state, relationship signals, response policy, and the allow decision.
  4. respond() 构建防御性不可变上下文；记忆和调用方指令按不可信 user 数据传递。
    respond() builds a defensive immutable context; memory and caller instructions remain untrusted user data.
  5. Provider 生成文本；身份门禁通过后返回结构化结果，否则返回稳定错误。
    The provider generates text; the identity gate returns a structured result or a stable error.
{
  "emotional_state": "EmotionalState(...)",
  "relationship": {"boundary_triggered": false, "...": "..."},
  "response_decision": "ResponseDecision(...)",
  "allowed": true
}

注意：公开结果包含 dataclass/不可变映射，而不是保证可直接 JSON 序列化的纯字典 schema。调用方应明确适配；稳定 JSON schema 是后续工作。
Public results contain dataclass/immutable mapping values rather than a guaranteed JSON-ready schema. Callers must adapt explicitly; a stable JSON schema remains roadmap work.

推荐部署边界 / Recommended deployment boundary

  1. 固定 Python 3.11+ 与依赖锁；从 wheel 安装。
  2. 每个用户会话或工作线程创建独立 Tang。
  3. 把状态路径放入受限目录；不要共享未加锁状态文件。
  4. Provider 出网使用 allowlist、秘密管理、超时与审计；不要记录原始敏感上下文。
  5. 工具和设备动作必须由宿主在权限检查后执行；保持默认拒绝。

8. 具体流程、包与证据 / Concrete flows, package, and evidence

记忆流程 / Memory flow

ConsentGate.grant(category) → MemoryStore.store(MemoryItem) → 按类别检索或衰减/移除。未同意写入被拒绝；该流程由调用方显式触发且仅驻留进程内。
ConsentGate.grant(category) → MemoryStore.store(MemoryItem) → category retrieval or decay/removal. Writes without consent are rejected; callers wire this process-local flow explicitly.

权限与工具流程 / Permission and tool flow

宿主提出能力请求 → 权限策略按主体、动作和上下文判断 → 扩展清单与准入检查限制能力上限 → 沙箱/模拟器验证 → 只有宿主执行器可产生外部效果。紧急授权必须显式、限时且可撤销。
A host requests capability → permission policy evaluates subject, action, and context → manifest/admission limits the authority ceiling → sandbox/simulation validates it → only a host actuator may create an external effect. Emergency authority must be explicit, time-bounded, and revocable.

9. 安全与隐私边界 / Security and privacy boundaries

已有控制 / Present controls

  • 身份/不变量前置与输出验证 / identity and invariant prechecks plus output validation
  • 记忆分类、同意与紧急态隔离 / memory categories, consent, emergency isolation
  • 上下文类型、角色、深度、数量和大小限制 / context type, role, depth, count, and size limits
  • 指令和记忆按不可信数据包装 / instructions and memory wrapped as untrusted data
  • Provider 异常映射为稳定类型 / provider failures mapped to stable types
  • 扩展准入、沙箱和负面测试 / extension admission, sandbox, negative tests

宿主责任 / Host responsibilities

  • 认证、租户隔离、速率限制 / authentication, tenant isolation, rate limits
  • 秘密管理、TLS 与出口策略 / secrets, TLS, egress policy
  • 加密、保留与删除 / encryption, retention, deletion
  • 审计与个人数据脱敏 / audit and personal-data redaction
  • 人审、工具幂等与补偿 / human approval, idempotency, compensation
  • 危机/医疗升级到真实服务 / crisis and medical escalation to real services

Provider 失败不会写入记忆、权限、工具或设备状态，但 process() 的人格交互状态可能已经推进。需要事务式重试时，应在独立实例/会话中由宿主协调。
Provider failure does not write memory, permission, tool, or device state, but persona interaction state may already have advanced. Hosts requiring transactional retries must coordinate them in isolated sessions.

12. 审查方法与结论 / Method and conclusion

本报告按代码优先原则核对公开入口、包配置、运行时模块、Provider、示例、测试、发布清单和活跃文档。没有把规范愿景、ADR 提案或关联仓库状态升级为当前实现事实。

This review used a code-first method across public entry points, packaging, runtime modules, providers, examples, tests, release manifests, and active documentation. Specification vision, ADR proposals, and related-repository status were not promoted into implementation claims.

结论：Tang OS 已形成边界清晰、可测试的核心参考实现，尤其适合验证“决策与表达分离”和“能力不等于权限”的架构原则；它距离生产平台的主要差距在跨层编排、数据治理、统一 schema、运行时收敛和运营证据。

Conclusion: Tang OS is a bounded, testable core reference implementation particularly useful for validating decision/expression separation and the rule that capability does not imply authority. Its remaining distance from a production platform lies in cross-layer orchestration, data governance, unified schemas, runtime convergence, and operational evidence.
